Esta página usa SolicitudForm como DTO de entrada: agrupa propiedades relacionadas para el binding y la validación. El enlace al ejemplo sin DTO aparece una sola vez al final de esta comparación.

DTO · ventajas
  • Un objeto mantiene juntos los campos de un formulario.
  • @Valid y las anotaciones centralizan reglas reutilizables.
  • La firma del controlador no crece con cada nuevo campo.
DTO · costes
  • Requiere una clase adicional y sus propiedades/accessores.
  • En un caso diminuto puede ser estructura innecesaria.
  • No es una entidad: por sí mismo no guarda datos.

Ambos ejemplos usan el Model de Spring MVC para preparar la vista. El Model es el contenedor MVC; no es el DTO. “Sin DTO” significa que el controlador recibe los campos como parámetros escalares.

El navegador ayuda; el servidor decide

HTML puede avisar con required, type=email, min, max, minlength y maxlength. Esto mejora la experiencia, pero se puede omitir desde el navegador o falsificar una petición.

Las anotaciones de SolicitudForm se ejecutan en el servidor mediante @Valid; el controlador comprueba además que un teléfono sea obligatorio cuando el canal elegido es TELEFONO. Toda regla relevante debe comprobarse en el servidor.

Thymeleaf genera HTML y presenta valores/errores; no es una frontera de seguridad ni sustituye la validación del controlador.

Sin persistencia

¿Dónde quedan los datos enviados?

Spring crea un SolicitudForm para la petición, lo rellena y pasa el mismo objeto a la vista de resultado. Vive en memoria durante el procesamiento de esa petición; no se escribe en un archivo ni en una base de datos.

Una variable local o un objeto en memoria desaparece al terminar su ciclo de vida o al reiniciar la aplicación. Una variable global compartida no es una solución: mezcla usuarios, puede sufrir accesos concurrentes y no se comparte de forma fiable entre varias instancias de la aplicación.

Para conservar solicitudes entre peticiones, reinicios o instancias hace falta persistirlas en un almacenamiento compartido, habitualmente una base de datos. No todas las aplicaciones necesitan una base de datos: este ejercicio no guarda nada porque su objetivo es practicar el flujo del formulario.

Al actualizar la vista de resultado, el navegador puede reenviar el POST. En una aplicación real se suele valorar POST/Redirect/GET; los datos no sobreviven al redireccionamiento por sí solos.

Recorrido: th:field enlaza controles; @ModelAttribute agrupa los valores recibidos; @Valid ejecuta reglas del servidor; BindingResult transporta errores; th:errors los presenta.
